ID一键登录重构 产品流程演示
V2 · 产品评审版

ACCOUNT LOGIN REDESIGN

判断的是“是不是同一个人”，不是“用了哪种登录方式”

用户可以先用手机号，也可以先用微信。系统最终要做的只有一件事：把经过验证的手机号和微信身份，落到正确的同一个用户账号里。

一条总规则

能证明是同一个人，就继续使用原账号；无法证明，或两个身份已经属于不同账号，就暂停自动处理。

01 / 先把概念说人话

微信身份只是“认人凭证”

它和手机号一样，是找到用户账号的方法，不是用户的订单、会员和权益本身。

UnionID 是什么？产品上可以理解为“同一个微信用户在 APP 和小程序之间的统一身份标记”。
02 / 租户配置

微信登录时，要不要强制绑定手机号？

这个开关只影响微信登录流程，不影响用户继续使用手机号登录。

微信登录强制绑定手机号

租户可根据业务需要决定：用户拿到微信身份后，能否直接进入系统。

当前：关闭用户授权微信后即可进入，不强制要手机号
关闭后的流程

微信授权完成即可登录

系统用微信身份查找原账号；找到就登录，找不到就创建一个微信用户。

03 / 登录流程演示

用户从哪个入口来，系统就走哪条路

点击下面三个场景，查看完整处理流程。

用户取消手机号授权开关关闭时不影响微信登录；开关开启时停留在手机号补充页，不创建半成品账号。
产品重点先取得用户同意，再做身份判断；不能因为手机号不同就直接创建第二个微信用户。
微信登录规则逻辑从上到下依次判断
  1. R1
    先查看原账号是否已经有手机号

    当微信身份已找到原账号，且原账号已有有效手机号时，系统直接登录，不重复要求手机号授权。

  2. R2
    租户开关关闭时

    当用户完成微信授权时，系统只根据微信身份查找账号；找到就登录，找不到就创建一个微信用户。

  3. R3
    租户开关开启且原账号没有手机号时

    系统要求用户补充手机号。用户拒绝时，不创建新账号、不写入半绑定关系，也不进入正式登录态。

  4. R4
    同一微信身份拿到不同手机号时

    系统继续使用原微信账号，把新号码作为换号或冲突问题处理，不能因为号码不同再创建一个微信用户。

  5. R5
    用户重复授权时

    相同微信身份、相同手机号再次提交，系统返回原来的登录结果，不重复建号、不重复发放权益。

通讯录是例外通讯录使用手机系统权限，与微信登录授权不是一回事，不能混在一起。
用户拒绝绑定微信保留手机号登录状态和已经完成的操作，不登出、不新建用户。
手机号登录规则逻辑微信绑定不能反过来阻断手机号登录
  1. R1
    手机号验证成功后，登录已经完成

    手机号已有账号时进入原账号；手机号没有账号时创建手机号用户。后续是否绑定微信，不改变本次登录结果。

  2. R2
    普通业务操作不强制微信授权

    用户点击直播、收藏、分享、我的、立即购买时，继续使用当前手机号账号完成操作。

  3. R3
    只有确实需要跨端同步时才邀请绑定

    例如用户主动进入账号中心绑定、开启跨端同步或准备跳转小程序。发起前必须说明绑定用途。

  4. R4
    用户拒绝微信授权时

    系统保留手机号登录状态、当前页面和已完成操作，不登出、不创建微信用户、不留下半绑定数据。

  5. R5
    微信身份已有归属时

    属于当前手机号账号则视为绑定成功；属于其他账号则立即停止绑定，进入账号冲突处理。

为什么不能自动合并？两个账号可能分别有订单、退款、余额、券和会员，合错一次就会把不同人的资产混在一起。
V1 怎么做？先拦截并记录冲突，提示用户双重验证；真实资产迁移不在本期原型范围内。
账号冲突规则逻辑任何入口、任何先后顺序都执行同一套规则
  1. R1
    冲突成立条件

    当微信身份已经属于账号 A，而本次验证的手机号已经属于账号 B 时，系统判定为两个账号冲突。

  2. R2
    系统立即停止自动处理

    不覆盖微信绑定、不把当前用户静默切到另一个账号、不创建第三个账号，也不自动搬运业务数据。

  3. R3
    要求用户分别证明两个账号都属于自己

    任意一个账号验证失败时，系统保持原有账号关系，不执行合并。

  4. R4
    验证通过后仍需检查业务资产

    订单、退款、余额、积分、券、会员和履约记录必须分别定义保留、迁移或冻结规则。

  5. R5
    重复提交不能产生不同结果

    同一次冲突处理无论用户点击多少次，系统只保留一条处理记录，并能追溯谁在什么时候做了什么。

04 / 身份判断演示

两种凭证分别查到了谁？

点击场景，直接查看系统最终应该怎么处理。

微信查找结果

没有找到历史账号

这是一个新的微信身份。

系统判断

两边都没有历史归属

可以确认不存在账号抢占问题。

处理结果

只创建一个新账号

将本次已验证的微信身份和手机号一起放进这个账号。

统一账号判断规则不受 APP、小程序或登录先后顺序影响
  1. 01
    两边都没找到账号

    创建一个新账号，并将本次已验证的身份放入该账号。

  2. 02
    只有一边找到账号

    继续使用找到的原账号；另一种身份未被占用时，补充绑定到原账号。

  3. 03
    两边找到同一个账号

    直接登录原账号，重复授权不重复创建数据。

  4. 04
    两边找到不同账号

    停止自动绑定与合并，进入账号冲突处理。

05 / 三个难懂案例

把“双手机号问题”翻译成人话

不再使用“反之也是”这种模糊描述，每个案例都给出明确结果。

手机号用户后来去小程序授权微信

关键不是“先从哪里登录”，而是本次验证的两个身份有没有历史冲突。

相同手机号可补绑
① 已有手机号账号

用户已用 139****0139 登录 APP，但还没有绑定微信。

→
② 小程序完成授权

如果授权手机号也是 139，且微信身份没有被别人占用。

→
③ 继续使用原账号

把微信身份补充到 139 账号，不再创建新用户。

手机号不同怎么办：不能只凭“可能是同一个人”强行合并；如果微信身份已有历史归属，直接进入账号冲突。

同一个微信身份，在小程序拿到了不同手机号

微信身份已经确认是同一个人，手机号不同可能只是换号。

不创建第二个用户
① 已有微信账号

这个微信账号原来绑定了手机号 138****0138。

→
② 小程序还是同一微信

即使这次用户授权了另一个手机号，也先登录原微信账号。

→
③ 处理手机号变化

新号码无人使用时走换号确认；已属于别人时进入冲突。

禁止做法：不能因为“新手机号不等于 138”就新建一个用户，否则同一微信身份会对应两个业务账号。

小程序先登录且没有手机号，后来 APP 用手机号登录

APP 和小程序看到的微信编号并不相同，跨端只能用微信统一身份判断是不是同一个人。

只比较微信统一身份
① 小程序已有微信账号

租户开关关闭，所以用户没有绑定手机号。

→
② APP 手机号账号绑微信

用户在确需跨端同步时，再完成微信授权。

→
③ 比较统一微信身份

相同则归到同一用户；不同则保持两个账号，不自动合并。

如果两边已经分别产生账号：即使微信身份相同，也先进入账号归一流程，确认订单、会员和权益怎么处理。

06 / 关键事件

手机号登录后，不要逢操作就拦微信授权

只有动作确实依赖微信身份时，才在用户理解用途后发起授权。

用户已用手机号登录

当前已经有可用账号和登录状态。

→
普通业务操作：直接继续

观看直播、收藏、分享、我的、立即购买，不因未绑微信而中断。

确需跨端同步：再邀请绑定

账号中心主动绑定、开启跨端同步、跳转小程序等场景，说明用途后授权。

通讯录：走系统权限

这是手机通讯录权限，不属于微信身份授权。

用户拒绝：保留当前状态

不登出、不撤销已完成操作，也不创建半绑定账号。

07 / 评审结论

这版需求最终只守三条底线

一人最终只落到一个正确账号

登录入口不同，不应导致订单、会员和权益被拆散。

无法证明是同一人，就不要合并

手机号相同、手机号不同或登录顺序，都不能替代真实身份判断。

两个已有账号冲突时，先停下来

不覆盖、不切号、不创建第三个账号，交给双重验证和受控处理。
